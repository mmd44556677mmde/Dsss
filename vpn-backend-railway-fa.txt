طرح فنی بک‌اند پنل VPN با Railway و سرورهای مستقل
نسخه: ۱ | تاریخ بررسی منابع: ۱۹ نوامبر ۲۰۲۶

این سند «طرح ساخت» است، نه یک نرم‌افزار آماده یا تضمین حقوقی. فرض نمونه: پنلی برای ثبت‌نام، مدیریت اشتراک، ساخت دستگاه، دریافت تنظیمات WireGuard، اندازه‌گیری مصرف و مدیریت چند سرور. اگر محصولت پروتکل، کشور، روش پرداخت یا تعداد کاربر متفاوتی دارد، برخی تصمیم‌ها باید عوض شوند.

==================================================
۱) جواب کوتاه به سؤال Railway
==================================================

Railway را برای پنل و API و پایگاه داده در نظر بگیر، نه برای عبور دادن ترافیک VPN کاربران. در زمان بررسی، سیاست استفاده قابل قبول Railway صراحتاً راه‌اندازی proxy و anonymization service را ممنوع می‌کند [۱]. در یک پاسخ پشتیبانی نیز اجرای proxy و tunneling service ممنوع اعلام شده است [۲]. پنل مدیریتیِ بدون عبور ترافیک کاربران از Railway لزوماً به معنی تأیید Railway نیست: قبل از تولید، معماری دقیق و نقش پنل را برای پشتیبانی بفرست و تأیید کتبی بگیر. اگر تأیید ندادند، خود پنل را هم به ارائه‌دهنده‌ای منتقل کن که صراحتاً این استفاده را مجاز می‌داند.

راه رفع محدودیت، مخفی‌کردن ماهیت سرویس، تغییر نام آن، ارسال ترافیک داخل WebSocket، ساخت حساب جایگزین یا دور زدن محدودیت حساب نیست. راه قابل اتکا جداسازی پنل از مسیر ترافیک، انتخاب میزبان مجاز و گرفتن تأیید است. در صورت محدود شدن حساب، سرویس مورد اعتراض را متوقف کن و از پشتیبانی درباره اصلاح و بازیابی سؤال کن.

از نظر فنی نیز شبکه عمومی Railway برای HTTP/HTTPS و TCP Proxy مستند شده، نه برای ورودی عمومی UDP [۳، ۴]. پشتیبانی UDP بین سرویس‌های شبکه خصوصی به معنی پشتیبانی UDP از اینترنت نیست [۵]. WireGuard معمولی از UDP استفاده می‌کند. بنابراین UDP آن را روی VPS مجاز و دارای IP عمومی اجرا کن. TCP Proxy عمومی Railway هم مجوز عبور دادن ترافیک VPN نیست.

==================================================
۲) معماری کلی: تفکیک کنترل و ترافیک
==================================================

                   ارتباط مدیریتی HTTPS
کاربر/مرورگر  ------------------------------>  پنل و API روی Railway
                                                  |        |
                                             PostgreSQL   Redis
                                                  |
                                         job/worker + outbox
                                                  ^
                               درخواست HTTPS خروجی دوره‌ای Agent
                                                  |
                                Agent روی VPS مستقل مجاز
                                                  |
کلاینت کاربر  ---- UDP مستقیم ---->  WireGuard روی همان VPS ----> اینترنت

Control plane = احراز هویت، پنل، اشتراک، سفارش، دستگاه‌ها، تعیین وضعیت مطلوب، گزارش و مدیریت نودها؛ در Railway فقط پس از تأیید مورد استفاده.
Data plane = اتصال VPN واقعی، رمزنگاری و عبور بسته‌ها؛ روی VPS مجاز. ترافیک کاربران از Railway، دیتابیس Railway یا Agent عبور نمی‌کند. Agent فقط تنظیمات و شمارنده‌ها را مدیریت می‌کند.

مدل پیشنهادی: یک برنامه API، یک worker، PostgreSQL و در صورت نیاز Redis در محیط Railway؛ روی هر VPS یک Agent کوچک و WireGuard. برای شروع می‌توان worker را جداگانه و Redis را فقط در صورت نیاز واقعی اضافه کرد. دیتابیس منبع حقیقت است؛ Redis منبع حقیقت اشتراک یا مصرف نیست.

فرض‌ها: حدود ۱۰۰ کاربر آزمایشی، ۱ تا ۳ نود، سهمیه حجمی و تاریخ انقضا، یک دستگاه = یک جفت کلید و یک peer. برای ظرفیت واقعی، بار و هزینه را اندازه بگیر؛ این اعداد تضمین نیستند. ظرفیت هر نود به CPU، پهنای باند، فاصله کاربران، خروجی شبکه و سیاست میزبان بستگی دارد.

==================================================
۳) فناوری‌های پیشنهادی و ساختار پروژه
==================================================

نمونه عملی: Python 3.12+، FastAPI، SQLAlchemy و Alembic، PostgreSQL، Redis برای rate limit و صف در صورت نیاز، یک worker مستقل، Docker، و Agent با Python یا Go. زبان می‌تواند عوض شود؛ تضمین‌های تراکنش و امنیت نباید عوض شوند. زمان‌ها همه UTC و حجم‌ها واحد byte به صورت bigint باشند. پنل وب می‌تواند جدا باشد، اما API باید بدون وابستگی به UI کار کند.

ساختار پیشنهادی:
backend/

  app/config.py               اعتبارسنجی تنظیمات و secrets
  app/auth/                   نشست، رمز، MFA و مجوزها
  app/users/                  کاربر و نقش
  app/catalog/                پلن‌ها
  app/subscriptions/          چرخه اشتراک و سهمیه
  app/devices/                کلید عمومی و تخصیص آدرس
  app/nodes/                  ثبت نود، heartbeat و desired state
  app/usage/                  ingestion و محاسبه مصرف
  app/payments/               سفارش، webhook و تطبیق پرداخت
  app/audit/                  رویداد امنیتی
  app/worker/                 outbox، اعلان و پاکسازی
  migrations/                 Alembic
  tests/                      unit / integration / security

ماژول‌ها را اول به شکل modular monolith بساز. شکستن به ده‌ها microservice در MVP پیچیدگی و هزینه ایجاد می‌کند. schema version و migration را با کد نگه دار؛ secret هرگز داخل مخزن نباشد.

==================================================
۴) مدل داده و قواعد اصلی
==================================================

کلید اصلی تمام جدول‌ها UUID و همه foreign keyها همراه محدودیت و index باشند. موارد زیر حداقل مدل هستند؛ created_at و updated_at و حذف نرم در جاهایی که لازم است اضافه شوند.

- users: id، email_normalized UNIQUE، password_hash، status، created_at. ایمیل را به شکل یکسان نرمال کن؛ وضعیت active/disabled.
- sessions: id، user_id، refresh_token_hash UNIQUE، expires_at، revoked_at، last_used_at. توکن خام در DB ثبت نشود.
- admin_roles و user_roles: نقش admin/support/user؛ اجازه‌ها سمت سرور اعمال شوند.
- plans: id، name، price_minor، currency، duration_seconds، quota_bytes nullable، device_limit، active. مقدار NULL سهمیه یعنی نامحدود؛ صفر یعنی بدون سهمیه.
- orders: id، user_id، plan_id، price_snapshot، currency، status، provider، provider_order_id UNIQUE، idempotency_key و created_at. وضعیت pending/paid/failed/expired/refunded. UNIQUE(user_id, idempotency_key).
- payment_events: provider، provider_event_id، order_id، payload_hash، processed_at؛ UNIQUE(provider, provider_event_id).
- subscriptions: id، user_id، plan_id، status، starts_at، expires_at، quota_bytes nullable، used_bytes bigint default 0، revision bigint. محدودیت سقف و مدت هنگام خرید snapshot شوند تا تغییر پلن قدیمی‌ها را ناخواسته عوض نکند.
- nodes: id، region، endpoint_host، endpoint_port، server_public_key، tunnel_cidr، status، desired_revision، last_seen_at، agent_version. کلید خصوصی سرور در VPS می‌ماند. برای شروع هر نود CIDR جدا داشته باشد.
- node_credentials: id، node_id، credential_hash یا شناسه گواهی، expires_at، revoked_at، last_used_at. دسترسی credential فقط به همان node محدود شود.
- devices: id، user_id، subscription_id، name، client_public_key، status، created_at، revoked_at. کلید عمومی معتبر و یکتا؛ کلید خصوصی در DB ذخیره نشود.
- assignments: id، device_id، node_id، tunnel_ip، desired_state، revision، allocated_at، released_at. unique فعال برای (node_id, tunnel_ip) و (node_id, device_id) با partial unique index یا جدول تخصیص مجزا؛ قواعد انتقال آدرس روشن باشد.
- usage_samples: id، node_id، agent_epoch، sequence، observed_at، received_at، sample_digest، payload/location. UNIQUE(node_id, agent_epoch, sequence). ثبت دقیق دوره نمونه‌گیری برای dedup و بررسی اختلاف.
- peer_counters: node_id، assignment_id، counter_epoch، last_rx، last_tx، last_sequence، updated_at. رکورد وضعیت تجمیع برای هر peer.
- usage_ledger: id، subscription_id، assignment_id، sample_id، rx_delta، tx_delta، occurred_at؛ UNIQUE(sample_id, assignment_id). رویدادهای immutable و قابل حسابرسی، بدون محتوای ترافیک.
- outbox: id، type، aggregate_id، revision، payload، status، attempts، next_attempt_at. ایندکس برای jobهای آماده.
- audit_events: actor_id، action، target_type/id، outcome، request_id، created_at و metadata بدون secrets.

FK، CHECK برای اعداد نامنفی و ایندکس روی subscription_id، status/expires_at، node_id و user_id ضروری است. همه استعلام‌های مشتری باید مالکیت منبع را علاوه بر احراز هویت بررسی کنند. منابع حذف‌شده‌ای که برای حسابداری لازم‌اند را پاک فیزیکی نکن. قوانین نگهداری و پاک‌سازی را از ابتدا تعیین کن.

قواعد عملیاتی: دستگاه باید متعلق به صاحب اشتراک باشد؛ فقط اشتراک فعال، داخل بازه زمانی و دارای سهمیه اجازه peer فعال دارد. محدودیت تعداد دستگاه باید با قفل یا constraint در تراکنش بررسی شود، نه صرفاً با شمارش در UI. تغییرات مهم با audit ثبت می‌شوند.

==================================================
۵) چرخه کامل از ثبت‌نام تا اتصال
==================================================

۱. کاربر ثبت‌نام می‌کند؛ ایمیل تأیید می‌شود؛ password با Argon2id و پارامتر مناسب هش می‌شود. rate limit روی ثبت‌نام، ورود، بازیابی و ارسال ایمیل اعمال شود.
۲. کاربر پلن و نود مجاز را انتخاب می‌کند. API با idempotency key سفارش pending می‌سازد و به درگاه مورد تأیید هدایت می‌کند. قیمت از DB و snapshot سفارش می‌آید، نه از مرورگر.
۳. درگاه webhook می‌فرستد. API امضای رسمی، زمان، event id، شناسه سفارش، مبلغ و ارز را با سفارش تطبیق می‌دهد؛ نتیجه پرداخت را در صورت نیاز با API درگاه به‌صورت server-to-server تأیید می‌کند. redirect مرورگر اثبات پرداخت نیست.
۴. در یک تراکنش: رویداد یکتا درج، سفارش در صورت تأیید paid، اشتراک ایجاد یا تمدید و outbox نوشته شود. webhook تکراری همان نتیجه را می‌دهد، بدون تمدید دوباره. پرداخت ناموفق یا ناسازگار اشتراک نمی‌سازد. برای refund، تراکنش جدید و سیاست مشخص لغو/بدهی تعریف کن.
۵. کلاینت ترجیحاً روی دستگاه کاربر جفت کلید WireGuard می‌سازد و فقط public key را به API می‌فرستد. در صورت نبود کلاینت سفارشی، باید کاربر کلید را در محیط امن بسازد و public key را در پنل وارد کند. تولید کلید خصوصی در سرور جایگزین پرریسک‌تری است و در این طرح انجام نمی‌شود. فایل تنظیمات بدون کلید خصوصی را صادر کن تا کاربر آن را محلی تکمیل کند؛ هرگز secret را داخل URL، لاگ یا ایمیل قرار نده.
۶. API در تراکنش اشتراک را قفل می‌کند، فعال بودن، سقف دستگاه و ظرفیت نود را بررسی می‌کند؛ آدرس اختصاصی از pool نود می‌گیرد؛ device و assignment را می‌سازد، desired_revision نود را افزایش می‌دهد و outbox می‌نویسد. پاسخ ۲۰۲ همراه operation_id؛ ساخت رکورد به معنی اعمال موفق روی نود نیست.
۷. Agent طبق بخش ۶ وضعیت مطلوب را می‌گیرد، اعتبارسنجی و اعمال می‌کند و revision اعمال‌شده را گزارش می‌دهد. UI ابتدا pending و فقط پس از تأیید Agent active نشان دهد. عدم پاسخ نود => pending/error، نه موفقیت ساختگی.
۸. کاربر تنظیمات endpoint نود، public key سرور، آدرس tunnel، DNS توافق‌شده و AllowedIPs لازم را در برنامه WireGuard وارد می‌کند. کلاینت مستقیم به IP/hostname و UDP port همان VPS وصل می‌شود. در full tunnel، مسیر پیش‌فرض ترافیک به VPN است؛ split tunnel فقط مسیرهای مشخص را عبور می‌دهد. قبل از انتخاب، رفتار IPv4، IPv6 و DNS را روی هر سیستم‌عامل آزمایش کن.
۹. Agent دوره‌ای شمارنده peerها را می‌فرستد. مصرف به ledger افزوده می‌شود. با انقضا، اتمام سهمیه، لغو یا حذف دستگاه، desired_state غیرفعال و revision افزایش می‌یابد؛ Agent peer را حذف و تأیید می‌کند. سیاست تأخیر و قطع ارتباط در بخش ۷ توضیح داده شده است.

تمدید: فرمول از پیش انتخاب و به کاربر نمایش داده شود؛ مثال: اگر اشتراک هنوز فعال است، expiry جدید = max(now, expiry قبلی) + مدت جدید؛ برای اشتراک منقضی از now. سهمیه تازه باید در یک دوره جداگانه یا رکورد جدید ذخیره شود تا مصرف دوره قبل دوباره شمرده نشود. برای سادگی MVP تمدید را با ایجاد subscription period جدا و یک قاعده مشخص برای دوره فعال پیاده کن؛ روی subscription فعال هم‌زمان constraint بگذار. خرید مجدد، refund و chargeback باید idempotent باشند.

==================================================
۶) طراحی Agent و همگام‌سازی
==================================================

Agent لازم نیست پورت ورودی مدیریتی عمومی داشته باشد. هر نود با یک هویت مستقل و HTTPS معتبر به API کنترل متصل می‌شود. اعتبار اولیه کوتاه‌عمر و یک‌بارمصرف را از کانال امن به VPS بده؛ سپس گواهی کلاینت یا توکن محدود به node_id و قابل چرخش بگیر. secret را با مجوز فایل محدود، خارج از مخزن و بکاپ عمومی نگه دار. تغییر نود یا افشای اعتبار => revoke و صدور مجدد. تمام درخواست‌ها را بر اساس هویت سرور احراز کن؛ node_id ارسال‌شده به تنهایی قابل اعتماد نیست. ارتباط TLS و اعتبارسنجی hostname اجباری است.

چرخه پیشنهادی: هر ۱۵ تا ۳۰ ثانیه با jitter، heartbeat و GET desired state بفرست؛ اعداد مثال‌اند و با بار آزمایش تنظیم شوند. Backend فقط assignmentهای همان نود، revision یکنواخت و lease expiry کوتاه برمی‌گرداند؛ pagination یا snapshot کامل versioned برای حجم زیاد. response باید revision ثابت و کامل داشته باشد تا Agent به‌علت pagination نیمه‌کاره peerها را حذف نکند. در اختلال با exponential backoff و jitter دوباره تلاش کن.

محتوای desired state: node_id، revision، generated_at، valid_until و فهرست peer شامل assignment_id، public_key، tunnel_ip/32، وضعیت و زمان انقضای مجاز. هیچ کلید خصوصی کاربر، رمز یا دیتای پرداخت ارسال نشود. Agent فقط پس از دریافت snapshot کامل و معتبر، پیکربندی را به شکل idempotent reconcile می‌کند: اضافه/به‌روزرسانی peerهای لازم و حذف peerهایی که دیگر مجاز نیستند. تغییرات را serialize کن؛ سپس revision و نتیجه را ack کن. revision قدیمی اعمال نشود. اگر اعمال بخشی ناموفق شد وضعیت degraded بده و تا رسیدن به وضعیت مطلوب retry کن. انجام تغییر DB و تغییر روی VPS تراکنش مشترک ندارند؛ برای همین pending، revision، تکرارپذیری و reconcile الزامی است.

برای اجرای WireGuard از ابزارهای استاندارد و یک رابط محدود استفاده کن. Agent نباید ورودی shell قابل تزریق را به command تبدیل کند؛ public key و IP را با validator و فراخوانی argv بدون shell بررسی کند. اجرای کم‌دسترسی، تفکیک بخش دارای مجوز شبکه از فرایند اصلی و systemd hardening پیشنهاد می‌شود. وضعیت local و صف اندازه‌گیری با ذخیره پایدار و دسترسی محدود نگهداری شود؛ Agent بتواند بعد از reboot به وضعیت معتبر برسد.

حالت قطع control plane: تصمیم محصول است و باید صریحاً به کاربر گفته شود. پیشنهاد محافظه‌کارانه fail-closed: Agent فقط تا valid_until آخرین snapshot مجاز به حفظ peer است و پس از پایان lease، peerهای تحت کنترل را غیرفعال می‌کند؛ به محض بازگشت API reconcile می‌کند. این کار از ماندگاری بی‌نهایت اشتراک لغوشده جلوگیری می‌کند، اما در قطعی API اتصال کاربران را هم قطع می‌کند. به ساعت UTC، همگام‌سازی NTP، جهش ساعت، persist امن lease و تست reboot توجه کن. اگر fail-open انتخاب شد، دسترسی و مصرف اضافی در قطعی ممکن است و SLA آن باید مشخص شود.

==================================================
۷) اندازه‌گیری مصرف و اعمال محدودیت
==================================================

WireGuard شمارنده‌های انتقال peer می‌دهد، نه گزارش وب‌سایت‌های بازدیدشده. تعریف قراردادی روشن: rx = byte دریافت‌شده سرور از peer و tx = byte ارسال‌شده سرور به peer؛ برای سهمیه مجموع rx+tx یا هر معیار دیگر را از ابتدا مشخص کن. overhead و روش اندازه‌گیری ممکن است با مصرف واقعی ISP تفاوت داشته باشد. محتوای ترافیک یا مقصدها برای محاسبه لازم نیستند.

هر Agent در زمان نمونه‌گیری برای هر assignment: counter_epoch، مقدار cumulative rx/tx، و زمان نمونه را در یک batch با agent_epoch و sequence یکنواخت در spool پایدار ثبت می‌کند. batch را تا پاسخ ثبت موفق نگه دارد و در retry همان شناسه و payload را بفرستد. پس از ack آن را حذف کند. صف باید ظرفیت، هشدار و سیاست پرشدن مشخص داشته باشد؛ در حالت اجرای سهمیه سخت، هنگام پر شدن queue به‌جای حذف بی‌صدا، peerها را متوقف یا دسترسی را محدود کن.

API هویت نود و تعلق assignmentها را چک می‌کند. داخل یک تراکنش با قفل رکورد شمارنده، ابتدا batch را با unique(node_id, agent_epoch, sequence) ثبت می‌کند. اگر batch تکراری با digest یکسان بود فقط ack قبلی بده؛ اگر همان شناسه با payload متفاوت بود خطای امنیتی بده. برای هر peer در همان counter_epoch، delta = current - previous و باید غیرمنفی باشد. ledger و subscriptions.used_bytes و baseline و پردازش batch در همان تراکنش commit شوند. پردازش برای هر نود باید مرتب باشد؛ batch خارج از ترتیب را تا رسیدن ترتیب لازم رد یا موقتاً نگه دار. sequence gap را تشخیص بده و alert بده. هم‌زمانی workerها نباید مصرف را دو بار حساب کند.

هنگام reset شمارنده، حذف و افزودن peer، reboot یا بازسازی interface، Agent باید epoch شمارنده را تغییر دهد و در صورت امکان پیش از reset نمونه نهایی را به spool پایدار بنویسد. شروع epoch جدید از شمارنده صفرِ شناخته‌شده با تأیید ترتیب رویداد انجام شود؛ نمونه اول آن epoch، delta از صفر است. اگر reset بدون نمونه نهایی یا از دست رفتن spool رخ داد، مصرف بازه نامشخص است: incident و وضعیت usage_uncertain ثبت کن و مطابق سیاست، دسترسی را متوقف یا رسیدگی دستی کن؛ عدد گمشده را حدس نزن. استمرار ترتیب، crash بعد از اعمال و قبل از ثبت epoch، و peerهای ایجادشده خارج از Agent از سناریوهای دشوارند و نیازمند تست عملی و طراحی journal پایدار هستند. از نمونه‌گیری و replay باید با محیط واقعی WireGuard آزمون گرفت.

زمانی که quota تمام یا expires_at گذشته است، وضعیت اشتراک و desired state در تراکنش تغییر می‌کند. سپس Agent در اولین poll آن را اعمال و ack می‌کند. چون نمونه‌ها و اجرای فرمان دوره‌ای‌اند، سهمیه حجمی و لغو فوراً و دقیقاً روی مرز تضمین نمی‌شوند؛ حتی با fail-closed تأخیر poll، داده در پرواز، قطعی و ساعت وجود دارد. برای محدودیت سخت، اعمال محلی قابل اتکا روی نود با بودجه و هماهنگی بین نودها لازم است. طرح ساده MVP سقف تقریبی دارد؛ حداکثر اضافه‌مصرف احتمالی را با نرخ واقعی × تأخیر انتشار/اعمال، به‌علاوه بسته‌های در پرواز تخمین بزن و پایش کن؛ اگر سرعت یا زمان قطعی نامحدود باشد، این هم کران تضمینی نیست. به مشتری وعده قطع دقیق نده.

ساعت مرجع اشتراک سمت سرور UTC است؛ Agent نیز expires_at و lease را محلی رعایت کند. در طول انتقال یک دستگاه به نود دیگر، peer قبلی اول غیرفعال و ack شود، سپس peer جدید فعال شود؛ در نود آفلاین برای جلوگیری از دسترسی هم‌زمان تا پایان lease قبلی صبر کن. از reuse آدرس تا زمان حذف peer قبلی اطمینان حاصل کن.

پاسخ خطا: {error:{code,message,request_id}}؛ ۴۰۰ ورودی، ۴۰۱ احراز هویت، ۴۰۳ مجوز، ۴۰۴ منبع پنهان/ناموجود، ۴۰۹ تعارض، ۴۲۹ محدودیت، ۵۰۳ وابستگی ناموجود. endpointهای تغییر وضعیت idempotent باشند. کلید idempotency با hash درخواست و نتیجه، محدود به کاربر/عمل و دارای زمان نگهداری است؛ استفاده با بدنه متفاوت => ۴۰۹. پاسخ config با Cache-Control: no-store؛ public key با private key تفاوت دارد ولی فایل‌های کامل ساخته‌شده محلی حساس‌اند.

مثال حداقلی config که کاربر کلید خصوصی خودش را محلی وارد می‌کند:
[Interface]
PrivateKey = <CLIENT_PRIVATE_KEY_KEPT_ON_DEVICE>
Address = 10.42.1.10/32
DNS = <TRUSTED_DNS_IP>
[Peer]
PublicKey = <NODE_PUBLIC_KEY>
Endpoint = <VPS_HOST>:51820
AllowedIPs = 0.0.0.0/0

این صرفاً نمونه IPv4 و full tunnel است؛ برای IPv6 باید به‌صورت کامل آدرس‌دهی، route، firewall و تست نشت داشته باشی یا IPv6 را طبق سیاست کلاینت عملاً مسدود کنی. حذف ::/0 به تنهایی جلوی نشت IPv6 خارج از تونل را نمی‌گیرد. DNS باید قابل دسترسی و مورد اعتماد باشد، وگرنه اتصال یا حفظ حریم خصوصی مختل می‌شود. تنظیمات ip_forward، NAT یا routing، firewall و پورت UDP روی VPS وابسته به سیستم‌عامل و شبکه ارائه‌دهنده است و باید در محیط مجاز آزمایش شود.

==================================================
۹) امنیت و حریم خصوصی
==================================================

- برای کاربران وب session cookie با Secure، HttpOnly و SameSite مناسب، CSRF protection برای عملیات تغییر وضعیت و محدودسازی CORS به originهای مشخص. Access token کوتاه‌عمر و refresh token چرخشی با امکان revoke؛ عدم ذخیره توکن در localStorage ترجیح دارد. تنظیمات مطابق معماری واقعی انتخاب شود.
- Admin: MFA اجباری، نقش کمترین دسترسی، ثبت علت عملیات حساس، تأیید دوم برای تغییرات پرخطر، و در صورت امکان محدودسازی شبکه ورودی در لایه‌ای که واقعاً پشتیبانی می‌شود. هرگز به هدر IP ارسال‌شده توسط مشتری اعتماد نکن؛ فقط پس از تأیید مدل proxy قابل اعتماد و مسیر ورودی از آن برای rate limit استفاده کن.
- password با Argon2id، مقادیر تصادفی رمزنگاری‌شده برای token، نگهداری hash توکن، بدون log رمز، توکن، فایل config کامل یا کلید خصوصی. key rotation و روند از دست رفتن credential را از پیش مشخص کن.
- DB و Redis روی شبکه خصوصی و بدون پورت عمومی در حالت عادی؛ حساب‌های DB با حداقل دسترسی. در محیط چند سرویس، تنظیمات DNS و اتصال IPv6 را طبق مستندات Railway آزمایش کن [۵]. Secrets در تنظیمات امن پلتفرم، جدا برای staging و production.
- VPS: سیستم به‌روز، firewall با UDP سرویس و فقط دسترسی مدیریتی ضروری، SSH با کلید و بدون root login مستقیم، عدم نصب Agent با دسترسی بیشتر از نیاز، ثبت و چرخش کلیدهای سرور. SSH مدیریت را روی Railway اجرا نکن. حفاظت DDoS، سیاست abuse و نرخ ارسال را با ارائه‌دهنده VPS روشن کن.
- داده حداقلی: فقط اطلاعات ضروری حساب، فاکتور و شمارنده مصرف. بدون جمع‌آوری مقصدها و محتوای ارتباط مگر مبنای قانونی و رضایت معتبر وجود داشته باشد. retention و حذف، دسترسی پشتیبانی، کشور نگهداری داده و وظایف GDPR یا قوانین مرتبط را با مشاور بررسی کن. «ناشناس بودن کامل» یا «صفر لاگ» بدون اثبات عملی و حقوقی ادعا نشود.
- از SSRF جلوگیری کن: URL نود و مقصد webhook نباید دلخواه و قابل دسترس به آدرس‌های داخلی باشند؛ endpointهای Agent صرفاً خروجی ثابت پیکربندی شده داشته باشند. محدودیت حجم درخواست، timeout، dependency pinning و اسکن آسیب‌پذیری در CI.

==================================================
۱۰) استقرار مرحله‌به‌مرحله
==================================================

پیش‌نیاز: تأیید کتبی Railway برای control plane و مجوز VPS برای ارائه VPN؛ دامنه، روش پرداخت قانونی، ایمیل تراکنشی، مخزن خصوصی و برنامه بکاپ. اطلاعات واقعی را در مخزن ثبت نکن.

الف) آماده‌سازی نرم‌افزار
۱. مخزن پروژه و dependency lockfile بساز؛ API، worker، migration و Agent را با تست‌های محلی اجرا کن.
۲. Docker image کم‌حجم و non-root بساز؛ سرویس HTTP روی 0.0.0.0 و متغیر PORT اعلام‌شده Railway گوش دهد. health endpoint بدون نیاز به ورود. migration را یک job/مرحله مستقل و یک‌بار در هر release اجرا کن، نه توسط تمام replicaها به صورت هم‌زمان.
۳. staging و production را جدا کن؛ کلید، دامنه، DB و webhook test جدا داشته باشند. ابتدا روی staging آزمون end-to-end بگیر.

ب) استقرار روی Railway پس از دریافت تأیید
۱. پروژه و محیط production بساز؛ PostgreSQL را با storage پایدار و backup مناسب ایجاد کن. API و worker را سرویس جدا تعریف کن؛ Redis را در صورت نیاز اضافه کن. DB و Redis را public نکن. اتصال با آدرس‌های private داخلی Railway، پورت صحیح و سازگاری IPv6 تنظیم شود.
۲. Variables لازم: DATABASE_URL خصوصی، REDIS_URL در صورت نیاز، APP_ENV، PUBLIC_BASE_URL، SESSION_SECRET/کلید امضا، اطلاعات ایمیل، PAYMENT_SECRET و AGENT_AUTH تنظیم شود. مقادیر واقعی را فقط در سیستم مدیریت secret قرار بده. از secret جدا برای هر نقش و محیط استفاده کن.
۳. دامنه HTTPS سفارشی پنل را اضافه و DNS و گواهی را طبق Dashboard بررسی کن. API می‌تواند با frontend هم‌دامنه یا پشت reverse proxy مجاز کار کند. HTTPS، SNI و محدودیت‌های HTTP edge را بررسی کن [۳]. Webhook درگاه باید یک URL HTTPS معتبر داشته باشد.
۴. migration را قبل از عرضه نسخه سازگار اجرا کن؛ بعد API و worker را deploy کن. readiness، اتصال DB و نمونه درخواست را تست کن. روشن بودن replica بیشتر از یکی به معنی جلوگیری از اجرای تکراری worker نیست؛ از قفل/claim با FOR UPDATE SKIP LOCKED و عملیات idempotent استفاده کن.
۵. backup زمان‌بندی‌شده و مستقل از همان محیط تهیه کن و restore آزمایشی انجام بده؛ backup volume به تنهایی برای بازیابی در پروژه یا محیط دیگر کافی فرض نشود [۶]. DB را بسته به امکانات و هزینه با backup سازگار و قابل بازیابی محافظت کن.

ج) آماده‌سازی هر VPS
۱. میزبان و منطقه مجاز انتخاب کن؛ IP عمومی و UDP مناسب بگیر؛ OS را به‌روزرسانی و firewall را تنظیم کن.
۲. WireGuard را از بسته رسمی سیستم نصب و کلید سرور را روی همان VPS تولید و محافظت کن؛ فقط public key و endpoint را در پنل ثبت کن. محدوده IP هر نود جدا و بدون تداخل با شبکه‌های محتمل کاربران انتخاب شود.
۳. forwarding، firewall و NAT/routing و DNS مورد نظر را پیکربندی و با یک peer آزمایشی بررسی کن؛ برای full tunnel محدودیت‌ها و IPv6 را طبق بخش ۸ تست کن. اجرای VPN نیازمند امکانات شبکه میزبان است؛ روی کانتینر معمولی Railway فرض نکن موجود است.
۴. Agent را به شکل service با restart policy اجرا و credential مستقل نود را به‌صورت امن provision کن؛ سپس heartbeat و دریافت revision را در پنل بررسی کن. هیچ کلید خصوصی سرور به API فرستاده نشود.
۵. یک حساب آزمایشی و دستگاه بساز؛ اتصال، اینترنت، DNS، مصرف، حذف peer، انقضا، قطع API، reboot و بازیابی را تست کن. وضعیت active تنها با ack Agent.

د) انتشار و rollback
نسخه‌های backward-compatible API/Agent و schema را مرحله‌ای منتشر کن. مهاجرت مخرب را پس از مهاجرت کد و گرفتن بکاپ انجام بده. rollback برنامه الزاماً rollback دیتابیس نیست؛ migration و سازگاری را از قبل طراحی کن. از credential و کلید خصوصی سرور بکاپ رمزنگاری‌شده جداگانه با کنترل دسترسی داشته باش؛ دسترسی به بکاپ کلید به معنی امکان impersonation سرور است. بازیابی در VPS تازه را تمرین کن.

==================================================
۱۱) محدودیت‌های عملی، هزینه و ریسک
==================================================

- سیاست Railway: پروکسی/ناشناس‌سازی طبق متن ممنوع؛ کنترل‌پلین مستقل را حتماً پیش از استقرار دقیقاً از پشتیبانی استعلام کن. موافقت ارائه‌دهنده VPS نیز جداگانه لازم است.
- شبکه: HTTP عمومی Railway با TLS، SNI و محدودیت‌های edge کار می‌کند؛ raw TCP سرویس جداست؛ هیچ‌کدام جای UDP عمومی WireGuard نیست. ارتباط private سرویس‌های Railway هم از اینترنت قابل استفاده مستقیم توسط VPS نیست. Agent از بیرون از طریق endpoint HTTPS عمومی احراز هویت‌شده ارتباط می‌گیرد.
- IP خروجی ثابت Railway برای allowlist در سرویس مقصد است، نه IP ورودی و نه جایگزین VPS. ویژگی، پلن، تعداد و اشتراکی‌بودن IPها را قبل از تکیه بررسی کن [۷].
- فایل‌سیستم کانتینر را برای داده دائمی فرض نکن؛ PostgreSQL/volume و بکاپ مناسب به‌کار ببر. داده صف مصرف Agent هم باید بعد از restart روی VPS باقی بماند.
- هزینه = هزینه واقعی API/worker و DB/Redis و storage/backup و egress پنل + هزینه VPSها + egress واقعی VPN و IP و DDoS + ایمیل و درگاه + عملیات. تعرفه‌ها و پلن‌ها متغیرند؛ قبل از سفارش از صفحه رسمی و فاکتور واقعی تأیید کن [۸]. قرار دادن VPN روی VPS به معنی حذف هزینه پهنای باند آن VPS نیست.
- مثال صرفاً فرضی: اگر هزینه ثابت VPS ماهانه ۱۰ دلار و هزینه ترافیک اضافه ۰٫۰۲ دلار به ازای هر GB باشد، با ۱۰۰۰ GB اضافه هزینه VPS = ۳۰ دلار، بدون احتساب پنل، مالیات و موارد دیگر. این قیمت واقعی یا پیشنهاد خرید نیست.
- سیاست مصرف، abuse complaint، نگهداری داده، تحریم‌ها/دسترسی به پرداخت و قوانین کشور عملیات و مشتریان را با ارائه‌دهندگان بررسی کن. قابلیت فنی تضمین پذیرش یا دسترسی از همه کشورها نیست.

==================================================
۱۲) پایش، تست و برنامه حادثه
==================================================

پایش حداقلی: نرخ خطا و latency API، DB connection و فضای ذخیره، تأخیر outbox، age آخرین heartbeat و applied_revision هر نود، مصرف CPU/RAM و network نود، صف مصرف و قدیمی‌ترین batch، تعداد peer فعال، ظرفیت IP، میزان تفاوت revision، شکست webhook، وضعیت backup و هزینه. هشدار عملیاتی تعریف کن؛ داده خام یا کلید را به log نفرست. request_id در سراسر گردش استفاده شود.

آزمون‌های ضروری:
۱. ثبت‌نام، ورود اشتباه، MFA ادمین، CSRF، rate limit، بررسی مالکیت device و محدودیت نقش.
۲. دو درخواست هم‌زمان برای آخرین slot دستگاه یا IP: فقط یکی موفق شود. صدور idempotency تکراری با همان و بدنه متفاوت.
۳. webhook تکراری و هم‌زمان، مبلغ/ارز اشتباه، امضای نامعتبر، ترتیب متفاوت رویدادها و refund.
۴. قطع شبکه Agent، retry، پاسخ تکراری، revision قدیمی، اعمال ناقص، حذف و reboot، پایان lease و reconnect. هیچ وقت applied قبل از ack نمایش داده نشود.
۵. batch تکراری و خارج از ترتیب، reset شمارنده، reboot، spool پر، crash بین مراحل DB، کمبود نمونه و مصرف هم‌زمان چند نود؛ ledger و aggregate باید سازگار بمانند.
۶. انقضا و سهمیه، تغییر ساعت، نود آفلاین هنگام revoke و انتقال، کامل بودن IPv4/IPv6/DNS؛ اضافه‌مصرف و زمان قطع با معیار واقعی اندازه‌گیری شود.
۷. تست بازیابی backup در محیط مجزا، rollback نسخه، بار کنترل‌پلین، هشدارها و قطع VPS. لاگ‌ها نباید secrets داشته باشند.

Runbook: در افشای credential نود، آن را revoke کن، نود و peerها را طبق سیاست محدود کن، credential جدید بده و audit را بررسی کن. در خرابی VPS، آن را از انتخاب خارج کن، صبر برای انقضا/حذف peerهای قدیمی طبق lease، سپس انتقال کنترل‌شده به نود سالم. در خرابی DB/API: به کاربران وضعیت بده، بکاپ را بر اساس RPO/RTO از پیش تعیین‌شده بازیابی کن، سپس reconcile تمام نودها و تطبیق ledger. در اخطار Railway: ترافیک یا سرویس مورد اعتراض را متوقف و با پشتیبانی همکاری کن؛ صرف جابه‌جایی نام یا پنهان‌سازی راه‌حل نیست.

==================================================
۱۳) ترتیب ساخت MVP و معیار پذیرش
==================================================

فاز ۰ ـ تصمیم‌ها: تأیید میزبان‌ها، مشتری و کشور، سیاست داده، نوع VPN، تعریف سهمیه، مدت lease، تحمل قطعی و بودجه. بدون این تصمیم‌ها طراحی نهایی نیست.
فاز ۱ ـ API و داده: کاربران، sessions، پلن، subscription، migration و تست مجوز؛ خرید و مدیریت ادمین دستی آزمایشی.
فاز ۲ ـ یک VPS و یک Agent: ثبت نود، کلید عمومی، تخصیص IP تراکنشی، snapshot/revision/ack و حذف peer. تست ارتباط واقعی با کلاینت WireGuard.
فاز ۳ ـ مصرف: spool، epoch، batch یکتا، ledger و گزارش؛ اعمال تقریبی سهمیه و expiration با بیان محدودیت‌ها.
فاز ۴ ـ پرداخت واقعی: تأیید webhook و تطبیق سفارش، refund، تراکنش و تست idempotency با sandbox درگاه.
فاز ۵ ـ تولید: امنیت، پایش، backup/restore، استقرار staging و production، سیاست abuse و تست بار. پس از آن اضافه‌کردن نودها و قابلیت انتقال.

معیار تحویل MVP: کاربر مجاز می‌تواند دستگاه بسازد و فقط پس از ack وصل شود؛ غیرفعال‌سازی طبق سیاست lease اعمال می‌شود؛ مصرف تکراری شمرده نمی‌شود؛ قطع API و reset شمارنده رفتار مستند دارند؛ پرداخت تکراری تمدید تکراری نمی‌کند؛ داده با تست restore بازیابی می‌شود؛ و ارائه‌دهندگان استفاده مورد نظر را تأیید کرده‌اند.
